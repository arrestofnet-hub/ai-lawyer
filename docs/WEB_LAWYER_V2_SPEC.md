# AI Lawyer Kazakhstan — самостоятельный веб-юрист v2
Статус: техническое задание для разработки, без развёртывания в production.
Дата: 2026-11-15
Ветка: feature/web-lawyer-v2-spec

## 1. Цель и границы
Создать независимый клиентский сервис на ailawyer.kz, без обязательной учётной записи ChatGPT. Это НЕ «чат с шаблонами». Сервис должен вести юридическое дело по законодательству Республики Казахстан: изучать документы, проверять факты/законы, строить альтернативные процессуальные стратегии, готовить документы и корректировать позицию при новых доказательствах.

Существующий публичный ChatGPT/MCP-плагин не удалять и не ломать: он остаётся каналом продвижения и совместимой интеграцией. В отдельном веб-приложении использовать лучшие существующие инструменты, но не выдавать структуру/чеклист за полноценный анализ.

Задача не в том, чтобы «скопировать ChatGPT» или гарантировать выигрыш дела. Нужны воспроизводимая методика, проверяемые основания выводов, честное обозначение неопределённости и система контроля качества. Исключить автономную отправку исков, жалоб или персональных данных третьим лицам без явного подтверждения пользователя.

## 2. Принятая методика юридического разбора
Начальный ответ пользователю: краткая суть (20–30 слов) и только необходимые уточнения. После предоставления материалов:
1. Идентифицировать цель клиента и стадию дела; отдельно проверить материальное право и процессуальный путь.
2. Разобрать каждое доказательство с реквизитами и страницей: оригинальный текст, дата, автор, подпись/способ удостоверения, сумма, участники, полномочия, приложения, источник.
3. В реестре хранить отдельно: [ДОКУМЕНТ/ПОДТВЕРЖДЁННЫЙ ФАКТ], [УТВЕРЖДЕНИЕ СТОРОНЫ], [ГИПОТЕЗА], [ТРЕБУЕТ ПРОВЕРКИ]. Не допускать перехода из гипотезы в установленный факт без доказательства.
4. Создать хронологию; найти расхождения дат, сумм, подписей, уведомлений, последовательности действий, версий разных лиц и пропуски подтверждающих документов.
5. Проверить нормы по официальным источникам РК с учётом юридически значимой даты и редакции. Отобразить название акта, статью/пункт, ссылку, дату редакции и применимость к конкретному факту; не ссылаться на непроверенные статьи, вымышленные судебные акты.
6. Построить не менее двух разумных маршрутов, если дело допускает альтернативы: основной, альтернативный; указать ожидаемые возражения противоположной стороны, слабые места, судебные/внесудебные препятствия, доказательства для истребования, сроки и основания.
7. Выдать последовательный план действия: кто, куда, какой документ, правовая цель, процессуальный срок/обоснование, что изменит тактику.
8. Создать проекты документов без выдуманных реквизитов с возможностью редактирования и экспорта DOCX/PDF. Ввести контроль качества перед экспортом: сторона, адресат, предмет, просительная часть, приложения, доказательства, нормы.
9. После нового документа обновлять историю дела и пересматривать ранее сформированную стратегию; фиксировать, что и почему изменилось.

Обязательные выходы для углублённого анализа: (a) вывод и уровень доказанности, (b) таблица противоречий со ссылками на документы/страницы, (c) правовые нормы с датой/источником, (d) стратегия и контраргументы, (e) недостающие доказательства, (f) ближайший процессуальный шаг.

## 3. Модули продукта
A. Веб-чат: вход на ailawyer.kz, адаптивная мобильная версия, потоковая выдача ответа, загрузка PDF/DOCX/изображений, отдельные карточки дел.
B. Менеджер дел: постоянная отдельная память по case_id, стороны, роли, стадия, цель, документы, факты, версии, сроки, история изменений, текущая стратегия и ближайший шаг; недопустимо смешение данных пользователей или разных дел.
C. Документный конвейер: приём, антивирус/контроль формата и размера, безопасное хранение, извлечение текста, OCR для сканов, разметка страниц/абзацев, проверка корректности извлечения, возможность ручного исправления; защита от prompt injection в файлах.
D. Доказательственный модуль: извлечение дат/сумм/подписантов, сопоставление нескольких документов, ссылки на страницу и фрагмент, таблица противоречий, классификация степени доказанности.
E. Законодательный поиск (RAG): официальные источники НПА РК, редакции на дату события и на сегодня, нормализованный индекс и журнал обновлений; отключить неподтверждённые ссылки. Ошибка zan.gov.kz не должна приводить к выдуманной норме.
F. Оркестратор стратегии: типизированные шаги intake → evidence → law → alternatives → adversarial_review → action_plan → draft → quality_gate; вызовы инструментов с сохранением результатов, проверками и версионированием.
G. DOCX/PDF: шаблоны юридических документов, корректная шапка, просительная часть, приложения, редактируемый Word; PDF после проверки.
H. Тесты и аудит: измерение правильности, пропущенных доказательств, ложных норм, смешения дел, ошибок OCR, устойчивости к недобросовестным инструкциям в загруженных документах; журнал действий без утечки содержимого.
I. Экономика/тарифы: телеметрия токенов, времени, числа страниц, OCR, поиска и хранения; квоты и лимиты для защиты расходов. Платежи — ПОСЛЕ испытаний.

## 4. Реализация и изоляция
- Сохранить действующий https://mcp.ailawyer.kz/mcp и GitHub main без изменений до готовности отдельной ветки.
- Предпочтительный старт: фронтенд React/Next.js, серверная оркестрация на текущем Node.js либо отдельном изолированном API (конкретная реализация после ревизии инфраструктуры); обработка документов изолированными workers. API ключи модели только на сервере.
- Не запускать крупную языковую модель локально на VPS 2 vCPU/4 GB; использовать внешнюю модель через платный API лишь после проверки условий обработки персональных данных и расходов. Сервер — для логики, хранения в допустимой юрисдикции и доступа.
- Не полагаться на исходную Supabase в Токио для хранения персональных данных граждан РК: спроектировать локальное хранение базы/цифровых объектов в Казахстане. Трансграничная передача и отправка содержимого в модель требуют отдельной законной схемы, прозрачного уведомления, минимизации/редактирования и контроля.
- Разграничение tenant/user/case на уровне БД и backend, шифрование, резервные копии, ограничение доступа, удаление данных, аудит изменений.
- Сайт, политика конфиденциальности и реальная работа памяти должны соответствовать друг другу.

## 5. Критерии приёмки (до продаж)
1. Пользователь открывает своё дело спустя 7 дней: история, загруженные документы, стратегия и следующий шаг на месте.
2. Сервис не показывает материалы одного клиента другому и не переносит факты между двумя делами одного клиента.
3. Для двух документов, где суммы 1 200 000 и 1 650 000 тг на одну дату, указано точное расхождение 450 000 тг, обе цитаты и юридическое значение; нельзя ограничиться перечнем критериев сравнения.
4. Для несовпадающих дат уведомления, уступки и регистрации раздельно фиксируются доказанный факт и версия стороны, приводится запрос недостающих первичных документов.
5. Недействующая/неподтверждённая норма не выдаётся как действующая; при недоступном первоисточнике система явно говорит об ограничении проверки.
6. При новых доказательствах стратегия реально меняется, а причина изменения доступна пользователю.
7. Корректный редактируемый DOCX и идентичный по существу PDF без выдуманных имён, ИИН, номеров дел и статей.
8. OCR-ошибка, частично нечитаемая страница или отсутствующий лист помечаются для проверки, а не используются как надёжный факт.
9. Устойчивость к внедрённым в PDF инструкциям «игнорировать правила», раскрытию чужих дел и обходу лимитов.
10. Набор не менее 20–30 обезличенных учебных дел по исполнительным надписям, ЧСИ, кредитам, коллекторам, договорам, жалобам и судопроизводству; сравнить ответы с эталонным анализом, оценивать критические ошибки отдельно.
11. Логи затрат позволяют расчитать стоимость одного простого ответа, одной страницы обработки, одного глубокого дела и DOCX/PDF, включая поиск/хранение.
12. Никаких гарантированных судебных исходов или автоматической подачи без подтверждения.

## 6. Порядок разработки
Этап 0. Инвентаризация действующего сайта/серверов, рабочей версии MCP и GitHub; проверить подписку Hoster, backup и рабочие DNS. Не ломать production.
Этап 1. Обособленный веб-чат на тестовом поддомене, авторизация, базовый вызов модели, отдельные case_id, контроль расходов и базовая безопасность.
Этап 2. Документный конвейер, факты, хронология, сравнение, ссылки на документы, постоянная память.
Этап 3. RAG по законодательству, проверка редакций, альтернативы и контраргументы, процессуальные стратегии.
Этап 4. Генератор Word/PDF, журнал изменений, качественные тесты на обезличенных реальных сценариях, меры защиты ПДн.
Этап 5. Закрытый пилот; только затем тарифы и платежи. Существовавшую гипотезу «10 бесплатных вопросов → кредиты» сохранить как идею, НЕ вводить без расчёта реальной себестоимости.
